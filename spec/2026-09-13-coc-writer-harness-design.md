## 1. 背景与定位

### 1.1 问题

COC（克苏鲁的呼唤）文字跑团中，守密人（KP）承担了远超主持工作的**叙事创作劳动**。对一份14.3万字符完整实录的统计分析显示，KP的1051条发言中高频创作劳动为：

1. **检定→分层结果描述**（全团150+次检定，每次现编成功/失败两个版本）
2. **场景到场开场白**（每处新地点连发3-6条：方位→光源声音→人群物件→异常点）
3. **NPC应答**（十余个有声线区分的NPC全天候接玩家的话）
4. **重复事件重述**（时间轮回等重复序列的措辞变体）
5. **前情提要**（每次续团手写摘要）

KP描述的形态是**节拍式短消息流**：平均35字/条、2-6条连发、一条一个节拍，而非文章。

### 1.2 定位

**KP的御用作家**：KP决定剧情走向，工具根据模组原文+会话上下文+KP文风，生成节拍式剧情描述供KP选用、删改。

工具内含两个AI角色，共同为KP减负：

- **作家**：把KP的剧情走向意图写成节拍式描述
- **助手**：把KP随手录入的玩家行动原文自动提炼为事件，维护事态笔记

- 作家与KP同样**全知**（守密人视角）：必须知道完整真相才能埋伏笔、写反讽、把握"点到为止"的分寸
- 作家遵守**写作纪律**而非工程过滤：给玩家的文本"描述证据、不点破因果"，这条来自规则书第十章的原则写进system prompt
- **KP留出调整空间**：每次生成均可编辑、重写、部分采用；KP编辑后的终稿落盘，成为会话记录与文风素材

### 1.3 非目标

- 不替代KP的剧情判断（走向、节奏、放水都归KP）
- 不做骰娘/规则引擎（骰子由群里现有骰娘负责；工具只把骰子结果当输入）
- 不做通用产品（自用工具，按KP本人习惯定制）
- 不做新手引导/防呆（用户即资深KP）

## 2. 关键设计决策记录

| 决策点 | 结论 | 备注 |
|---|---|---|
| 使用时机 | 备团预生成 + 跑团实时生成，两者都要 | 同一生成引擎，批量/交互两种驱动方式 |
| 用户 | 仅KP本人（本人即实录中的KP） | 深度定制文风与操作习惯 |
| 形态 | 本地Web应用，与QQ并排，复制粘贴进群 | 不接QQ bot，规避风控与工程量 |
| LLM后端 | 多provider抽象接口，优先GLM（已有key） | OpenAI兼容协议，可切换DeepSeek/Claude等 |
| 检索方案 | **不用RAG**：模组≤10万字量级，按场景重组后直接进上下文 | 结构化选取（场景图/NPC引用）替代语义检索 |
| 模组分类 | 线性（场景order链）/ 箱庭（场景网+多场景指针+事态感知） | 共用同一schema，靠使用方式区分 |
| 玩家行动感知 | **助手角色**：KP将玩家行动（对话形式）随手录入timeline窗口，助手自动提炼情节归入事态笔记 | 作家的上下文由此获得持续、低负担的事态来源 |
| 分线叙事 | v1支持：叙事线（threads）为一等概念，timeline按线打标，写作台线切换，合流时作家基于两线时间线生成汇合描述 | 通常最多双线并行；组间信息互通与否由KP按线设定 |
| 骰子与规则 | 非重点。作家仅持一条常识："玩家行为成败由骰子决定，KP可发奖励骰或跳过检定，检定结果服务于剧情" | 检定结果作为意图输入的一部分 |
| 架构重心 | **作家架构**：核心上下文 + 事态感知 + 写作素材库 | 否决早期"模组引擎/管家"方向（状态机、硬保密过滤、引导钩子、骰子模块全部移除） |
| 自由创作模式 | 后续计划（见13.1）：玩家背离模组时，在模组世界观下放开剧情走向，任故事自由发展 | v1不做，数据模型预留mode字段 |
| 玩家已知信息维度 | 后续计划（见13.2）：对立模组中玩家相互敌对、默认信息不互通，需按玩家/阵营维护"已知信息"，生成时只向受众揭示其可知内容 | v1不做；分线visibility是其组粒度先行版 |

三条铁律（来自AI跑团实践的失败教训，本设计的自然推论）：
1. 骰子和规则计算不交给LLM——本设计根本不做骰子
2. 走向决策归KP——工具只做表达
3. 长团记忆外置——事态笔记+素材库，不依赖上下文窗口

## 3. 总体架构

一套带持久化的作家harness，架在最小工程底座上：

```
┌──────────────── 前端（本地Web，三页）───────────────────┐
│  素材库 │ 写作台（主页面：意图生成+行动时间线）│ 会话页   │
└──────────────────────┬─────────────────────────────────┘
                       │ REST / SSE（流式生成）
┌──────────────────────┴─────────────────────────────────┐
│                 FastAPI 后端                             │
│   玩家行动助手（timeline录入 → 事件提炼 → 事态笔记）       │
│   上下文装配器 ← 素材库 + 事态笔记 + 文风锚点              │
│   生成编排器（写作守则+文风锚点 → 作家system prompt）      │
│   模组预处理器（PDF → 场景化素材，LLM辅助+人工校对）       │
│   LLM Provider 抽象（GLM优先）                           │
│   文件存储（data/目录JSON：模块库/会话库/生成记录）         │
└─────────────────────────────────────────────────────────┘
```

harness循环（跑团进行时的完整心跳，按叙事线各自运行）：

```
KP随手录入玩家行动（对话形式，归属当前线）→ 助手提炼事件 → 事态笔记更新
→ KP输入剧情意图 → 装配上下文（本线事态+场景素材+文风锚点）
→ 作家生成节拍流 → KP调整 → 终稿落盘（喂回本线recent_log与文风素材）→ 复制进群
```

## 4. 数据模型（文件存储，单用户）

存储为 `data/` 下的JSON文件，可直接手工编辑。不做数据库。

### 4.1 模组素材库 `data/modules/<mod_id>.json`

```yaml
module:
  id: amaranthine_desire
  title: 不息的渴望
  type: linear | sandbox            # 线性=场景order链；箱庭=场景网
  meta: {players, duration, ...}
  scenes:
    - id: mill
      name: 磨坊
      order: 2                      # 线性模组填主线序号；箱庭不填或松散
      location: 敦威治南郊
      text: "场景全部原文（预处理时重组归档）"
      condensed: "浓缩版（LLM生成、KP可改）"
      box_texts: [{text, usage}]    # 标记为"只可原文引用"的成品文本
      npcs: [hawkins]               # 关联NPC引用
      entry_conditions: "..."       # 进入条件（原文摘录或摘要）
      exits: [{to: town_road}]      # 场景图边（线性≈链，箱庭=网）
      drafts: {}                    # 备团预写稿（开场白/关键检定描述）
  npcs:
    - id: sarah
      name: 莎拉·布劳恩
      voice_card: {外貌, 特质, 扮演秘诀: [], 动机}   # 进上下文，决定声线
      knowledge_boundary: "..."     # 知情边界
      stats_ref: "附录B"            # 数值卡位置引用，不进生成上下文
  background:
    summary: "真相浓缩（LLM生成、KP可改）"
    original: "背景章原文（作家全量可见）"
```

检定表、线索、事件轴**不做结构化字段**——它们已写在场景原文里，作家直接读原文，保留模组散文质感与完整性。

### 4.2 会话状态（事态笔记）`data/sessions/<session_id>.json`

```yaml
session:
  id, module_id, title
  mode: module | free               # 模组模式（默认）/自由创作模式（后续计划）
  threads:                          # 叙事线（一等概念；不分线时仅1条主线）
    - id: thread_a
      name: 磨坊救援组
      members: [richard, mary]      # 在线PC
      current_scene: mill           # 本线场景指针
      visibility: shared | private  # 与其他线信息是否互通（KP设定）
  story_so_far: [事件1, 事件2, ...]      # 全局故事线（KP全知视角）：助手提炼或KP手记
  pcs: [{name, one_liner}]               # 每人一句话状态（助手可代更新）
  timeline: [                            # 玩家行动时间线（按线打标；全会的编年骨架）
    - {ts, thread_id: thread_a, raw: "玩家行动原文（对话形式）", events: [提炼的事件], source: assistant | manual}
  ]
  recent_log: "按线维护的滚动窗口（本线行动原文+生成终稿，自动截断）"
  generation_log: [                      # 生成记录（harness持久化核心）
    - {ts, thread_id, intent, context_snapshot, raw_output, final_output, mode}
  ]
```

**时间线与叙事线的关系**：timeline是按时间排序的全会编年骨架，thread是挂在每条timeline/生成记录上的视角分组——"何时发生了什么"与"谁知道这件事"由此解耦，分线、合流、信息互通控制都建立在这组关系上。

### 4.3 文风锚点 `data/style/profiles/default.json`

从KP本人日志提取：节拍模式（2-6条连发、≤60字/条）、过渡词（"那么/你们看到/此时"）、若干条原文few-shot样本（场景开场/检定结果/NPC对白各几条）、语言风格要点。一次提取，可手工增删。

## 5. 模组预处理管线

```
mods/*.pdf → PyMuPDF提取全文 → LLM辅助场景重组 → KP在素材库页校对 → module.json
```

- **场景重组**：LLM按章节/场景边界把原文切成scenes，生成condensed摘要，抽取NPC的voice_card字段；这是GLM擅长的批量结构化任务
- **人工校对**：素材库页逐场景显示原文+结构，KP确认场景切分、修正voice_card；校对是一次性成本
- 首批处理两份样例：《不息的渴望》（线性+时光圈事件轴）、《追书人》（箱庭轻度版/菜单式调查）
- 已知限制：《不息的渴望》附录NPC数值表为图片无法提取——本设计不依赖数值表，仅留stats_ref占位，无影响

## 6. 生成管线（写作台核心）

写作台上有两个AI角色：**作家**（6.1–6.4，把意图写成描述）与**助手**（6.5，把玩家行动提炼成事态）。分线/合流的作家侧操作见6.7。

### 6.1 作家输入

- **意图**（必须）：自然语言描述剧情走向，如"玩家进入磨坊，纵火后惨状，埋'楼梯没被烧'的线索"
- 可选参数：在场PC、骰子结果（如"理查德侦查失败"）、篇幅（几拍）、语气（压抑/日常/紧张）、上下文开关（选择哪些素材入上下文）
- 生成始终针对**当前激活线**（分线时写作台以标签页切换，作家一次只写一条线）

### 6.2 作家上下文装配

固定底座：写作守则 + 文风锚点。
动态部分（按token预算装配，超预算时text降级为condensed）：
**当前线**的场景材料（text或condensed + box_texts + 关联NPC的voice_card）+ 事态笔记（story_so_far/pcs）+ 本线recent_log + KP意图与参数。

**分线装配规则**：
- 上下文以当前激活线为中心：本线场景、本线成员、本线recent_log
- 全局story_so_far始终进入（作家保持全知）
- 他线事件：仅当该线visibility为shared、或KP在意图中明确指示（如"另一组的爆炸声隐约传来"）时，作为可写入的素材；private线的他线事件仅供作家把握全局，**不得进入面向本线玩家的文本**
- 合流后按6.7折叠

### 6.3 作家system prompt

内容（按优先级）：
1. 角色设定：KP的御用作家，与KP同样全知守密人视角
2. 输出形态：节拍式短消息流，2-6条，每条≤60字，标注类型（环境/动作结果/NPC对白/检定指令/结算）
3. 写作守则（源自规则书第十章）：第二人称现在时；描述证据不点破因果（"地毯上有泥"而非"凶手翻窗而入"）；box text只可原文引用；"少即是多"的怪物描写；NPC按声线卡说话、不越知情边界；骰子常识（成败由骰子决定，KP可发奖励骰/跳过检定，检定为剧情服务）
4. 文风锚点：KP的节拍模式、过渡词、few-shot样本

### 6.4 作家输出格式

LLM输出结构化JSON：`{beats: [{type, text}], state_update: {exposed_info: [], threads_opened: [], threads_closed: []}}`。前端渲染为可编辑的消息流列表；state_update作为"事态更新建议"展示，KP一键采纳进story_so_far。

### 6.5 助手：玩家行动提炼

**输入**：KP在写作台侧栏的timeline窗口随手录入玩家行动——直接粘贴群聊片段或快速敲入对话形式文本（如"理查德：'我去敲门' / 玛丽掏出十字架"），无需整理格式。录入自动归属当前激活线，可手动改挂他线。

**提炼任务**（异步执行，不打断KP）：
- 从行动原文中提取事件（"理查德敲门，无人应答"）
- 判定事态影响：story_so_far追加/合并事件、pcs状态一句话更新、事件归属线核对
- 更新该线recent_log滚动窗口

**输出**：提炼结果以差异预览形式显示（"将新增2条事件：…；玛丽状态更新为'右手受伤'——采纳？"），KP一键采纳或改用手工编辑。timeline保留raw原文与提炼结果的对应关系，作为可回溯的事实底账。

**续团前情提要**：同一助手的批量档——基于timeline与story_so_far生成下一场开场用的前情提要（KP实录中的手写劳动之一）。分线状态下可按线生成各自的"本线提要"。

### 6.6 备团批量模式（作家）

同一作家引擎：遍历场景列表逐一生成开场白、关键检定的成败两版描述，存入scene.drafts，备团时可编辑。开团后写作台可直接调出预写稿微调。

### 6.7 分线与合流（作家）

**分线**：KP在写作台拆分叙事线（通常最多双线；成员、场景指针、visibility各线独立设定），此后timeline、recent_log、场景指针均按线维护。两线可暂停/恢复切换，对应实录中"先过磨坊这边/回到教堂这边"的节奏控制。

**合流**：KP触发合流时，作家基于两线timeline与story_so_far生成汇合描述——重逢场景+情报交换的转述（谁向谁讲述了什么：由KP意图指定，或作家依据两线事件给出提议）。合流后线折叠为单线，两线事件并入全局story_so_far，recent_log合并。

## 7. UI（三页，极简）

1. **素材库**：模组导入与预处理进度、场景浏览/校对、NPC卡、文风锚点管理、备团批量预写
2. **写作台**（主页面）：左侧玩家行动时间线（随手录入→助手异步提炼→差异采纳，按线分组显示）；右侧线切换标签页、意图输入+可选参数、当前线场景指针、上下文开关、流式生成结果、逐条编辑/重生成、一键复制、预写稿调出、分线/合流操作
3. **会话页**：开新场/续团（续团前情提要由助手基于timeline生成）、save/load、生成记录与时间线回看

## 8. LLM Provider抽象

OpenAI兼容协议的统一接口（`chat(messages, **params)`），配置文件选择默认provider与模型。作家与助手共用provider抽象（可用不同模型档位：作家用高质量档，助手用快速便宜档）。首批实现GLM（zhipuai OpenAI兼容端点）。流式输出经SSE推送到写作台。

## 9. 错误处理

- LLM调用失败：自动重试1次，失败后在写作台显示错误与"重试"按钮，不丢意图输入；助手提炼失败则timeline保留raw原文、标记"未提炼"，可手动重触发
- 上下文超预算：场景text自动降级condensed并提示KP
- 输出JSON解析失败：降级显示原始文本流（beats切分退化为整段），不阻塞使用
- 数据文件损坏/缺失：启动时校验并明确报错（文件存储，可直接手工修复）

## 10. 测试策略

- **单元测试**：上下文装配（给定module/session/意图→黄金上下文快照，含分线场景下visibility过滤）、token预算降级、助手事件提炼（给定行动原文→黄金事件列表）、JSON schema校验、provider参数
- **质量评估集**：用《不息的渴望》真实日志回放——取实录中KP的实际描述（意图可从上下文反推），与本工具生成结果人工对比评分（贴合模组/文风/节拍/剧透控制四个维度）；助手提炼用实录玩家发言做回放测试（给定玩家行动序列→对比人工标注的事件）
- **端到端验收**：导入模组→校对→开会话→录入玩家行动→助手提炼→分线→双线生成→合流→编辑→落盘→续团提炼，全流程走通

## 12. 构建顺序

1. **工程底座**：git仓库、FastAPI骨架、provider抽象（GLM连通验证）
2. **预处理管线**：PDF→文本→场景重组→module.json（先做《不息的渴望》；校对初期直接编辑JSON，素材库页UI就绪后转为界面校对）
3. **会话状态与助手**：session模型（含叙事线threads）、timeline窗口、玩家行动提炼（含差异采纳UI）、续团前情提要、文风锚点提取
4. **写作台**：作家生成管线（场景开场白/检定结果/NPC对白三类先行）、流式输出、编辑与落盘、线切换与分线/合流操作
5. **备团批量**：预写稿生成与管理
6. **打磨**：事态更新建议、上下文开关、转场重述/日后谈等长文本模式
7. **（后续）自由创作模式与玩家已知信息维度**：见第13章

## 13. 后续计划

### 13.1 自由创作模式

**触发场景**：玩家行为持续背离模组剧情线（跑偏、即兴支线膨胀、把模组关键节点全部错过）。是否切换由KP人工判断，不做自动检测。

**模式定义**：保持模组的**世界观**（background真相、NPC档案、时代与基调）作为grounding，放弃**场景级原文约束**——不强求按模组剧情走向，任故事自由发展。作家从"模组场景的执笔者"切换为"世界观下的自由作家"。

**实现要点（届时细化）**：
- `session.mode: free`（数据模型已预留）
- 上下文装配变化：当前场景材料 → background（summary+original）+ 事态笔记 + timeline已确立的虚构事实 + recent_log；NPC声线卡继续生效（模组NPC可继续在场）
- 作家system prompt的写作守则不变（写作纪律与全知立场仍然适用），仅grounding来源切换
- 模式切换可回退：KP可随时切回module模式，继续用模组后续场景
- 自由模式下产生的新虚构事实（新NPC、新事件）应随timeline/事态笔记沉淀，成为会话内的新canon

### 13.2 玩家已知信息（视角维度）

**场景**：特定模组中玩家相互对立（PvP），默认玩家之间信息不互通——不仅是分线问题，即使在同一场景内，不同玩家所见所知也可能不同。

**方向（届时细化）**：
- "玩家已知信息"成为一等维度：按玩家（或阵营）维护已知事件/线索集合，来源为timeline事件按参与者与可见性过滤
- 生成时声明"受众"（在场PC），作家只向受众揭示其可知内容——分线visibility是组粒度的先行版，这是玩家/阵营粒度的细化
- 助手录入玩家行动时标记在场者，自动更新各玩家已知集合
- UI提供"某玩家此刻知道什么"的视角预览，供KP把握信息差与欺骗空间
