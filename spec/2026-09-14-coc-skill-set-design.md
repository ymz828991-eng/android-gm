# COC 跑团 Skill 集设计文档

- 日期：2026-09-14
- 状态：brainstorming 完成，待用户审阅
- 前置：本设计承接 `spec/2026-09-13-coc-writer-harness-design.md` 的**问题定义**（KP 创作劳动分析、节拍式产出形态、三条铁律、写作纪律），废弃其全部**实现方案**（Web 应用、FastAPI、React、JSON 数据模型、Provider 抽象、独立助手服务）。
- 参考架构：superpowers（skills 即行为协议 + 宿主 harness 注入引导）。本设计中 harness 就是 Claude Code 本身，不再新造。

## 1. 背景与定位

### 1.1 问题（继承自旧 spec，经日志验证）

COC 文字跑团中，KP 的核心创作劳动：检定分层结果描述、场景到场开场白、NPC 应答、重复事件重述、前情提要。产出形态是**节拍式短消息流**：2-6 条连发、每条一个节拍、约 35-60 字/条，有明确的过渡词习惯。

### 1.2 定位

**KP 的御用作家系统**：KP 决定剧情走向，skill 集根据模组素材 + 会话态势 + 文风锚点，产出节拍式描述草稿供 KP 选用、删改。KP 实际发出的终稿才是正史。

### 1.3 非目标（继承）

- 不替代 KP 的剧情判断（走向、节奏、放放水都归 KP）
- 不做骰娘/规则引擎（骰子由群里现有骰娘负责，检定结果只作为意图输入）
- 不做通用产品（自用，按 KP 本人习惯定制）
- 不写工程代码（本系统全部由 markdown 文件构成：skill、语料、状态）

### 1.4 三条铁律（继承，不可违反）

1. **骰子和规则计算不交给 LLM**——检定结果由 KP 带入意图
2. **走向决策归 KP**——系统只做表达
3. **长团记忆外置**——事态在文件，不依赖上下文窗口

## 2. 关键设计决策记录

| 决策点 | 结论 | 理由 |
|---|---|---|
| 运行时 | Claude Code 本身即 harness | 旧方案 90% 工程花在重建 harness（UI/状态服务/生成管线）上，价值其实在内容里 |
| 会话模型 | **双会话**：生产者 + 消费者 | 两角色上下文食谱不同：生产者吞原文流水（可脏可压缩），消费者需要干净装配（蒸馏态势+模组+锚点）。分立强制纪律：群聊到作家的唯一通路是状态文件 |
| 唯一真相 | 生产者的输入 | 消费者产出永远是草稿；KP 实际发出的版本贴回生产者成为正史。状态与文风素材只来自真实输出 |
| 进食节奏 | 增量 | 跑团中按自然节拍持续粘贴，生产者即时提炼 |
| 状态存储 | 分层文件：timeline.md（追加式）+ state.md（可重写摘要） | 增量读取在真正长的地方（timeline）自然成立；关键态势（state）小到可全读，免疫历史改写遗漏 |
| 读取协议 | 冷启动全量 / 会话内增量 两种模式 | 长团跨天、压缩后重开都需要无损恢复 |
| save/load | save 自动（生产者吸收即落盘），load 是冷启动协议 | 无专门存档动作；git 由收团沉淀 commit，形成可回滚存档点 |
| 语料库 | 两层：技法层（成体系）为主 + 片段层（只收"写错即穿帮"类） | 技法学手法上限高；片段防穿帮。种子来自规则书第十章与 KP 本人日志 |
| 构建顺序 | 核心回路优先，语料随团生长 | 旧 spec 死于先建工程再找价值；先验证风险最大的假设（实时回路质量） |
| 分线/自由模式等 | v2 | 它们是消费者 skill 的扩展段落和 state 字段，不是独立工程 |

## 3. 系统总览

```
                        CLAUDE.md（引导：路由表 + 铁律 + 文件协议）
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        ▼                            ▼                            ▼
   备团期skill                   跑团期skill                    收团期skill
  coc-prep 备团            coc-producer 生产者会话           coc-harvest 收团沉淀
  coc-pc-import 玩家导入   coc-consumer 消费者会话                │
        │                            │                            ▼
        ▼                            ▼                      corpus/ 语料库
  campaign/ 模组库 ◀──读取──  campaign/ 状态文件 ◀──追加/更新        （技法+片段+文风）
```

**唯一接口是文件**。skill 之间不互相调用，全部通过 campaign/ 与 corpus/ 的读写约定协作——这也是双会话并行无需同步机制的安全基础。

## 4. Skill 清单（v1：5 个 skill + 1 个引导文件）

| Skill | 目录 | 触发时机 | 职责 | 读写权限 |
|---|---|---|---|---|
| coc-prep 备团 | `.claude/skills/coc-prep/` | 新模组，一次性 | 四步管线（见 6.1） | 写 scenes/ npcs/ module.md routes.md drafts/ |
| coc-pc-import 玩家导入 | `.claude/skills/coc-pc-import/` | 开团前，每 PC 一次 | PC 背景 → 个人情节钩子 → PC 卡 + 场景挂注 | 写 runs/<团>/pcs/（挂注在 PC 卡，不改模组库） |
| coc-producer 生产者 | `.claude/skills/coc-producer/` | 跑团中，KP 粘贴群聊原文时 | 吸收→提炼→落盘→简报（见 6.3）；另有"前情提要"模式 | 追加 timeline.md，更新 state.md，其余只读 |
| coc-consumer 消费者 | `.claude/skills/coc-consumer/` | 跑团中，KP 给出写作意图时 | 读取协议→装配→生成→自检→呈现草稿（见 6.4） | campaign/ 全部只读 |
| coc-harvest 收团沉淀 | `.claude/skills/coc-harvest/` | 收团后，一次 | 完整性校验→语料沉淀→git commit 存档点 | 写 corpus/，读 timeline，git commit |

### 4.1 CLAUDE.md（引导文件，非 skill）

仓库根的 CLAUDE.md 是每次会话自动加载的引导，约 40 行，内容：

1. 仓库身份声明（COC 跑团工作台）
2. 会话职责判断与路由表（"这个会话该干什么"→ 哪个 skill）
3. 三条铁律
4. 文件协议摘要（目录结构、单一写者原则、两种读取模式）
5. W0 冷启动指令（会话开始时若 campaign/ 有未完结的团，先执行 load 协议）

这是 superpowers SessionStart hook 注入在本仓库的等价物（Shape C：宿主原生加载的指令文件）。

### 4.2 单一写者原则（联动安全的核心）

| skill | scenes/npcs | pcs | timeline.md | state.md | corpus/ | drafts/ | git |
|---|---|---|---|---|---|---|---|
| coc-prep | 写（KP 校对） | — | — | 初始化 | 读 | 写 | — |
| coc-pc-import | —（不改模组库） | 写 runs/<团>/pcs/ | — | — | 读 | — | — |
| coc-producer | 读 | 读 | **追加** | **更新** | — | 读 | — |
| coc-consumer | 读 | 读 | 读尾部 | 读全量 | 读 | 读 | — |
| coc-harvest | 写（收团模组修正，KP 确认） | — | 读 | — | **写** | — | **commit** |

timeline/state 只有生产者写，corpus 只有 harvest 写，消费者全程只读。

## 5. 文件布局与格式

```
coc_v2/
  CLAUDE.md
  .claude/skills/coc-{prep,pc-import,producer,consumer,harvest}/SKILL.md
  corpus/
    INDEX.md                  ← 索引：分类清单，消费者的检索入口
    techniques/               ← 技法层（成体系）
      写作纪律.md              ← 规则书第十章蒸馏：证据不点破因果、少即是多…
      节拍手法.md              ← 从 KP 日志挖掘：连发节奏、过渡词、异常点置尾…
      氛围营造.md  伏笔技巧.md
    fragments/                ← 片段层（只收"写错即穿帮"类，随团生长）
      creatures/  scenes/
    文风锚点.md               ← KP 的节拍模式 + few-shot 样本（一次提取，可手工增删）
  campaign/<模组名>/
    module.md                 ← 元信息 + 真相摘要 + 伏笔登记表（编号供 timeline/state 引用）
    routes.md                 ← 理想路线：主线、关键节点、可跳过项
    scenes/<中文名>.md        ← 场景卡（"PC 挂注"节永久留空）
    npcs/<中文名>.md          ← NPC 卡
    drafts/                   ← 预写稿（按场景组织）
    runs/<团名>/              ← 一次开团（同模组可多 run，2026-09-15 修订）
      pcs/<PC名>.md           ← 本团 PC 卡（挂注钩子在此）
      timeline.md             ← 本团事件流水，## 场次分节，只增不改
      raw.md                  ← KP 终稿逐字底账（开团记录 KP 标签，吸收时过滤归档，只增不改；harvest 挖文风样本的来源，2026-09-15 修订）
      state.md                ← 本团当前态势，随时可重写
      recaps/                 ← 本团每场前情提要
```

### 5.1 timeline.md 条目格式

```
#142 [2场] 理查德纵火失败，磨坊东翼焚毁；楼梯未过火（伏笔#3保住）
#143 [2场] 玛丽试图搀扶霍金斯，被拒绝
```

- 每条：编号 + 场次 + 一句话事实。编号全团连续，是消费者的读取游标
- 只增不改；生产者把每轮原文提炼为 1-3 条事实

### 5.2 state.md 格式（设计约束：一屏以内）

```
# 当前态势（截至 #142，第2场）
## 故事线（3-5句）
## PC状态（每人一行）
## NPC状态（仅变化过的）
## 线索台账（已暴露线索 + 对应伏笔编号）
## 当前位置与时间
```

### 5.3 场景卡 / NPC 卡内容清单

- **场景卡**：场景原文 + 浓缩摘要 + box_texts（标记"只可原文引用"）+ 出入口 + 在场 NPC 引用 + PC 挂注节（永久留空，挂注活在各 run 的 PC 卡）
- **NPC 卡**：声线卡（外貌、特质、扮演秘诀、动机）+ 知情边界；数值表仅留引用不进上下文

## 6. 协议细节

### 6.1 coc-prep 四步管线（每步停下等 KP 校对，校对=直接改 markdown）

1. PDF → 全文提取 → 场景切分（含 box text 标记）
2. 场景卡 + NPC 卡生成
3. 真相摘要（module.md）+ 理想路线分析（routes.md）
4. 预写稿：各场景开场白、关键检定的成败两版描述 → drafts/

### 6.2 coc-pc-import

读 PC 背景 → 对照真相与场景卡找连接点 → 生成个人情节钩子（该 PC 独有的线索、情感联结、与 NPC 的旧缘）→ 写 runs/<团名>/pcs/<PC名>.md，挂注只活在 PC 卡钩子里，不改模组库场景卡（2026-09-15 修订）。

### 6.3 coc-producer 吸收协议

1. 解析粘贴的原文（按说话人切分；KP 自己的消息是正史节拍，玩家消息是行动）
2. 提炼为带编号事件 → **追加** timeline.md；同时按 KP 标签过滤，将 **KP 终稿逐字**追加到 runs/<团>/raw.md——每批分节头下先列本批事件（照抄 timeline 条目）再接逐字原文，raw 可独立阅读且能从事件号反查（玩家原文不入档：语义在 timeline，逐字在 QQ 群；铁律3）
3. **更新** state.md（故事线/NPC 状态/PC 状态/线索台账/位置时间）
4. 极简变更简报（"新增 3 事件，NPC 状态改 1"），KP 可即时纠正

前情提要模式（续团时）：基于 timeline + state 生成本场 recap → recaps/，供 KP 发群。

### 6.4 coc-consumer 读取与生成协议（实时回路的心脏）

**读取（两种模式）**：

| 模式 | 触发 | state.md | timeline.md |
|---|---|---|---|
| 冷启动 | 会话开始/压缩后 | 全量 | **全量**，游标复位到最新 |
| 会话内增量 | 每次生成前 | 全量（小） | 尾部增量（自游标起） |

**装配**（每次生成前按序）：

1. state.md 全量 + timeline.md（按模式）
2. 按意图定位：场景卡（1-2 张）→ 在场 NPC 卡 → corpus/INDEX.md 按需取技法/片段
3. 固定底座：写作纪律（硬约束）+ 文风锚点（格式协议为硬约束，few-shot 为参照非上限——默认全力发挥，KP 令"贴合档"时才模仿 KP 文笔）+ module.md 真相摘要（作家全知视角的底座，备团时蒸馏、篇幅小）。含"发散/推荐走向"类意图时切换**提案模式**：面向 KP 豁免剧透纪律，产出 3-5 个跨类型走向提案（2026-09-15 修订）

**意图输入**：自然语言，如"玩家进磨坊，纵火后的惨状，埋'楼梯没烧'的线索；理查德纵火检定失败"；可选带骰子结果、语气、篇幅。

**生成与自检**：节拍草稿（2-6 条连发，标注类型：环境/动作结果/NPC对白/检定指令/结算）→ 自检（剧透：是否点破因果？box text 是否原文？NPC 是否越知情边界？节拍形态对不对？）→ 呈现。KP 反馈后局部重生成。**对 campaign/ 完全只读。**

### 6.5 coc-harvest 收团沉淀

1. 校验 timeline 完整性（编号连续、场次闭合）
2. 从本场**实际产出**（timeline 正史，非草稿）挖语料：确认有效的新技法、入库高价值片段、补充文风样本
3. 更新 corpus/ 与 INDEX.md
4. 模组修正：KP 口述本团发现的模组 bug 与即兴扩充 → 直接改模组库（场景/NPC/module/routes），标注团名；KP 本人任何时候也可手改。跑团中 skill 不写模组库，变化走 state，修正攒到收团（2026-09-15 修订）
5. `git commit`（本团一场一个存档点；state.md 误更新时可回滚）

## 7. 四条工作流

**W0 冷启动/加载**：任一会话开始时扫描 campaign/*/runs/ 下未完结的 run（多个并存时列候选等 KP 选——同模组多次开团、同时多团均合法）→ load 协议（6.4 读取表冷启动行；消费者额外读 routes.md + 当前场景卡恢复方位感）。隔天续团 = W0 + 生产者前情提要模式 + timeline 开新 `## 场次` 分节。"模型恢复记忆"与"玩家恢复记忆"是两个动作，分属 W0 与生产者。

**W1 备团**（一次性）：coc-prep 四步管线 → coc-pc-import 挂个人钩子。产出物 = 消费者的全部输入地基。

**W2 跑团实时**（双窗口并行）：

```
KP ──贴群聊原文──▶ 生产者：提炼→timeline追加+state更新→简报
KP ──给意图──────▶ 消费者：读取→装配→草稿→自检→呈现→KP逐条反馈→局部重生成
KP ──终稿发群───▶ 实际发出的版本贴回生产者 → 成为正史
```

**W3 收团**：coc-harvest 归档 + 语料沉淀 + git commit → corpus 生长 → 下次消费者更强。

## 8. 联动机制

1. **CLAUDE.md 路由**决定谁上场；skill 之间不互相调用
2. **单一写者原则**（4.2）使双会话并行无需同步机制
3. **草稿与正史分离**：正史唯一入口是生产者，状态和文风素材只来自真实输出
4. **防呆**：贴错窗口时 skill 自行识别（"这是写作意图，请到消费者窗口"/"这是群聊记录，我在吸收"）；消费者发现 timeline 断号时提醒先喂生产者

## 9. 语料库设计

- **技法层**（成体系，消费者学手法）：种子 = 规则书第十章写作纪律 + 从《不息的渴望》日志挖掘的节拍手法。每次收团由 harvest 确认/扩充
- **片段层**（只收"写错即穿帮"类）：神话生物描写等。起步近乎空，随团生长
- **文风锚点**：KP 节拍模式（连发节奏、过渡词、few-shot 样本），第一个团备团时从日志一次性提取。定位双层：格式协议（硬约束）+ 参照样本（非上限；贴合档的模仿目标）
- INDEX.md 是唯一检索入口：消费者先查索引再按需读条目

## 10. v1 范围与延后项

**v1**：CLAUDE.md + 5 skill + campaign/corpus 目录约定 + 文风锚点提取 + 用《不息的渴望》跑通备团管线 + 回放验收。

**延后到 v2**（均为消费者 skill 扩展段落 + state 字段，非独立工程）：分线/合流（state 预留 thread 字段位）、剧情偏离引导、自由创作模式、玩家已知信息维度、日后谈长文本。

## 11. 验收方式：回放测试

superpowers 式标准化验收。取《不息的渴望》日志的一段：喂当时的玩家发言与态势给消费者，将其生成的节拍与 KP 当年实际发的版本对比，按四维评分：贴合模组 / 文风 / 节拍形态 / 剧透控制。构建期每完成一层跑一次；调优语料后重跑。

## 12. v1 构建顺序

1. **底座**：git init；CLAUDE.md；campaign/corpus 目录与格式约定（本 spec 第 5 章）
2. **语料种子提取**（一次性）：文风锚点 + 技法层（规则书第十章蒸馏成写作纪律.md、从《不息的渴望》日志挖掘节拍手法.md）
3. **coc-prep**：对《不息的渴望》跑四步管线，KP 校对产出场景卡/NPC 卡/真相/路线/预写稿
4. **coc-consumer**：读取+装配+自检协议；首次回放测试
5. **coc-producer**：吸收+简报+前情提要
6. **coc-harvest**：沉淀 + commit
7. **全链路回放验收**：W0→W2 闭环模拟

构建顺序即风险顺序：地基质量（场景卡）直接决定回路质量，最先打磨。
